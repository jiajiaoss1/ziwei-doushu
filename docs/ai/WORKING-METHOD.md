# 工作方法：让产品持续迭代，而不是每次重来

> 问题不是「AI 不够聪明」，而是每次对话没有留下**决策、状态、下一步**。
> 这份文件定义我们怎么工作。

---

## 1. 一个循环

```text
观察（数据/研究/用户）
  → 问题定义（谁的什么问题）
  → 决策（做/不做/先做哪个）
  → 规格（PRD/SPEC/验收）
  → 实现（code/test）
  → 上线（deploy/verify）
  → 测量（metrics/回馈）
  → 记录（decision/changelog/handover）
  → 下一轮
```

没有「观察」与「问题定义」的改版，叫灵感，不叫产品迭代。

---

## 2. 每次工作 session 的固定动作

### 开始（5 分钟）

1. 读 `docs/README.md`
2. 读 `docs/operations/HANDOVER.md` 最后一行
3. 读 `docs/operations/BACKLOG.md` 的当前优先级
4. 确认今天只做哪一个 Requirement ID

### 结束（5 分钟）

1. 更新 `REQUIREMENTS.md` 状态
2. 更新 `BACKLOG.md`
3. 重大变更写 `CHANGELOG.md`
4. `HANDOVER.md` 追加一行
5. commit + push

> 这五步是为了让下一个 AI 不用重读 code 也能接手。

---

## 3. 每周节奏

| 时间 | 做什么 | 产出 |
|---|---|---|
| 周一 | 看数据／研究，选本周唯一赌注 | 一个 Problem Statement + 一个 Requirement ID |
| 周二–四 | 规格 → 实现 → 测试 | PR / spec |
| 周五 | 上线验证、看指标、复盘 | CHANGELOG + 下周 backlog |

如果没有数据，就用访谈/研究补；不要用「我觉得」代替。

---

## 4. 问题定义模板

任何产品改动前，先写清楚：

```md
### Problem
谁：____
在什么情境：____
现在怎么解决：____
为什么不够好：____
证据：____（访谈/数据/贴文）
如果我们不做，会怎样：____
```

没有这张卡，不进 SPEC。

---

## 5. 决策与规格

- 策略级 → ADR（`decisions/ADR-*.md`）
- 功能级 → PRD + SPEC
-  Bug → 直接修，但补 changelog

### ADR 模板

```md
# ADR-000X 标题
- 日期：
- 状态：Proposed / Accepted / Superseded
- 背景：
- 选项：
- 决定：
- 理由：
- 后果：
- 批准人：
```

### SPEC 模板

```md
# SPEC: 功能名
- Requirement ID：
- 目标用户：
- 问题：
- 范围（做/不做）：
- 流程：
- 文案：
- 边界/错误：
- 指标：
- 测试：
```

---

## 6. 研究与验证

- 先研究，再写文案，再改页面。
- 研究资料放 `research/`，原始资料不进 Git。
- 研究结论要能回答：「这会改变哪个决策？」
- 不要用「用户应该会喜欢」当证据。

---

## 7. 指标

- 先定义漏斗，再看数字。
- 没有 GA4 时，先用可得讯号（访谈、客服、社群）。
- 不以「PV 增加」当成功；要看诊断完成率、报告开启率、付费转化、退款。

---

## 8. 文件债

每周五花 10 分钟：

- 有没有文件与 code 不一致？
- 有没有 decision 没写进 DECISION-LOG？
- 有没有 backlog 重复？
- 有没有 archive 文件被当成现行？

有的话，下周第一件事就是修文件，不要让它累积。

---

## 9. 交接

`operations/HANDOVER.md` 是最重要的文件。
它不是给人看的历史，是给下一个 AI 的「执行上下文」。

每次交接必须写：

- 做到哪
- 没做完什么
- 为什么卡住
- 下一个具体起点
- 版本快照

---

## 10. 我们的节奏原则

1. **一次只赌一个问题**（不是一次改十个页面）
2. **先证据，后文案**
3. **先规格，后 code**
4. **先完成，再完美**
5. **每次结束都要让下一棒跑得动**
