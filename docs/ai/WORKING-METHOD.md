# 工作方法：讓產品持續迭代，而不是每次重來

> 問題不是「AI 不夠聰明」，而是每次對話沒有留下**決策、狀態、下一步**。
> 這份文件定義我們怎麼工作。

---

## 1. 一個循環

```text
觀察（數據/研究/用戶）
  → 問題定義（誰的什麼問題）
  → 決策（做/不做/先做哪個）
  → 規格（PRD/SPEC/驗收）
  → 實作（code/test）
  → 上線（deploy/verify）
  → 測量（metrics/回饋）
  → 記錄（decision/changelog/handover）
  → 下一輪
```

沒有「觀察」與「問題定義」的改版，叫靈感，不叫產品迭代。

---

## 2. 每次工作 session 的固定動作

### 開始（5 分鐘）

1. 讀 `docs/README.md`
2. 讀 `docs/operations/HANDOVER.md` 最後一行
3. 讀 `docs/operations/BACKLOG.md` 的當前優先級
4. 確認今天只做哪一個 Requirement ID

### 結束（5 分鐘）

1. 更新 `REQUIREMENTS.md` 狀態
2. 更新 `BACKLOG.md`
3. 重大變更寫 `CHANGELOG.md`
4. `HANDOVER.md` 追加一行
5. commit + push

> 這五步是為了讓下一個 AI 不用重讀 code 也能接手。

---

## 3. 每週節奏

| 時間 | 做什麼 | 產出 |
|---|---|---|
| 週一 | 看數據／研究，選本週唯一賭注 | 一個 Problem Statement + 一個 Requirement ID |
| 週二–四 | 規格 → 實作 → 測試 | PR / spec |
| 週五 | 上線驗證、看指標、復盤 | CHANGELOG + 下週 backlog |

如果沒有數據，就用訪談/研究補；不要用「我覺得」代替。

---

## 4. 問題定義模板

任何產品改動前，先寫清楚：

```md
### Problem
誰：____
在什麼情境：____
現在怎麼解決：____
為什麼不夠好：____
證據：____（訪談/數據/貼文）
如果我們不做，會怎樣：____
```

沒有這張卡，不進 SPEC。

---

## 5. 決策與規格

- 策略級 → ADR（`decisions/ADR-*.md`）
- 功能級 → PRD + SPEC
-  Bug → 直接修，但補 changelog

### ADR 模板

```md
# ADR-000X 標題
- 日期：
- 狀態：Proposed / Accepted / Superseded
- 背景：
- 選項：
- 決定：
- 理由：
- 後果：
- 批准人：
```

### SPEC 模板

```md
# SPEC: 功能名
- Requirement ID：
- 目標用戶：
- 問題：
- 範圍（做/不做）：
- 流程：
- 文案：
- 邊界/錯誤：
- 指標：
- 測試：
```

---

## 6. 研究與驗證

- 先研究，再寫文案，再改頁面。
- 研究資料放 `research/`，原始資料不進 Git。
- 研究結論要能回答：「這會改變哪個決策？」
- 不要用「用戶應該會喜歡」當證據。

---

## 7. 指標

- 先定義漏斗，再看數字。
- 沒有 GA4 時，先用可得訊號（訪談、客服、社群）。
- 不以「PV 增加」當成功；要看診斷完成率、報告開啟率、付費轉化、退款。

---

## 8. 文件債

每週五花 10 分鐘：

- 有沒有文件與 code 不一致？
- 有沒有 decision 沒寫進 DECISION-LOG？
- 有沒有 backlog 重複？
- 有沒有 archive 文件被當成現行？

有的話，下週第一件事就是修文件，不要讓它累積。

---

## 9. 交接

`operations/HANDOVER.md` 是最重要的檔案。
它不是給人看的歷史，是給下一個 AI 的「執行上下文」。

每次交接必須寫：

- 做到哪
- 沒做完什麼
- 為什麼卡住
- 下一個具體起點
- 版本快照

---

## 10. 我們的節奏原則

1. **一次只赌一個問題**（不是一次改十個頁面）
2. **先證據，後文案**
3. **先規格，後 code**
4. **先完成，再完美**
5. **每次結束都要讓下一棒跑得動**
